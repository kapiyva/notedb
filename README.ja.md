## note.db とは

note.db は、SQLite をパーソナルナレッジの基盤として使うための共通規約です。

タスク、メモ、アイデア、日記。これらを束ねるデジタル手帳には、ポータブルで永続的なオープン共通規格が存在しません。既存のノートツールはアプリごとに固有のフォーマットでデータを保存しており、ここに空白があります。

note.db は、この空白を埋めるための共通規約を定めます。ノートを表すテーブルの最小構造や命名のルールといった土台のみを規定し、具体的な表現は各フォーマット（特定のメソドロジーを表す DDL 群）に委ねます。共通の土台があることで、複数のフォーマットが同じ SQLite ファイルに共存し、ツールはフォーマットを越えて動作します。

ライブラリでも CLI でもアプリケーションでもなく、規約そのものです。誰でもこの規約に従ってフォーマットを公開したり、ツールを作ったりできます。

## なぜ SQLite か

思考の痕跡には、アプリより長い寿命が必要です。どのアプリが廃盤になっても、どのサービスが終了しても、手元に残り続けるべきものだからです。

SQL は数十年の実績を持つ、枯れたオープン規格です。書き留めた断片をビューで束ね直し、集計で傾向に気づき、検索で過去に立ち返る。手帳をめくり、思い出し、繋げ直すための語彙が、標準仕様の範囲で揃っています。

SQLite はその SQL を、単一ファイルで完結し、あらゆる環境で読み書きできる形で実装した、事実上の標準です。

同じ動機は、Markdown のようなファイル群でも一見満たせます。けれどファイルは独立した文書であり、横断して束ねる共通の手段を持ちません。タグや関係をどう表現するかはフロントマターやフォルダ構造といったゆるい慣習として個々のファイルとユーザーの規律に委ねられ、その慣習自体を配布し、別のツールで一貫して効かせる手立てもありません。note.db ではその役割を SQLite のスキーマに担わせます。フォーマットは DDL という配布可能な成果物であり、データベースを開いた時点で構造として効き、集計や横断検索は SQL として最初から備わっています。

## 規約

### 1. ノートテーブル

note.db の中心概念はノートテーブルです。以下のカラムを少なくともすべて持つテーブルをノートテーブルと呼びます。

```sql
id         TEXT PRIMARY KEY  -- UUID 推奨
title      TEXT              -- nullable
body       TEXT NOT NULL
created_at TEXT NOT NULL     -- ISO 8601
updated_at TEXT NOT NULL     -- ISO 8601
```

フォーマットはノートテーブルを1つ以上持たなければなりません。

`body` はノートの内容そのものであり、必須です。`title` は任意の見出しです。走り書き、日記、fleeting note など、多くのノートは本文だけで成立し、見出しを付けること自体がすべてのメソドロジーにあるとは限らない編集行為だからです。`title` が NULL のとき、クライアントは `body` の最初の1行をそのノートの表示ラベル（フォールバックラベル）として導出します。これにより、見出しを持たないデータに見出しを強制することなく、すべてのノートを一覧に表示できます。

ノートテーブルをどう使うかはフォーマット設計者が自由に決めてかまいません。たとえば Zettelkasten であれば、ノートテーブルを1つ持ちリンクを別テーブルで管理することも、種別（literature note / permanent note 等）ごとにノートテーブルを分けることも、どちらも規約を満たします。

### 2. 追加テーブル

フォーマットはノートテーブル以外のテーブル（タグ、リンク、設定など）を持ってもかまいません。複数のフォーマットが同一の SQLite データベースに共存できるため、テーブル名・ビュー名はすべて規約3のプレフィックスルールに従い、名前の衝突を防いでください。

### 3. プレフィックス

テーブル名とビュー名にはフォーマット名のプレフィックスを付けます。SQL 識別子はハイフンを使えないため、フォーマット名にハイフンが含まれる場合はプレフィックスではアンダースコアに置き換えます（例: フォーマット `cornell-notes` のプレフィックスは `cornell_notes`）。

プレフィックスより後ろの部分は単数形にします（例: `..._note`, `..._task`, `..._tag`。`..._notes` のような複数形は使いません）。名前が揃ううえ、プロパティテーブルの参照列名を `<テーブル名>_id` と機械的に導出できます（規約4参照）。

```
<format>_<table>      -- 例: zettelkasten_note, evergreen_note
<format>_<view>_view  -- 例: zettelkasten_graph_view（ビューは推奨、必須ではない）
```

### 4. プロパティテーブル

プロパティテーブルは、ノートに紐付くラベル付きの一対多の関係を表現します。以下をすべて満たすテーブルをプロパティテーブルと呼びます（フォーマットが `zettelkasten`、プレフィックスを除いたテーブル名が `fleeting` であるノートテーブル `zettelkasten_fleeting` に紐付くプロパティテーブルの例）。

```sql
fleeting_id  TEXT NOT NULL REFERENCES zettelkasten_fleeting(id)
label        TEXT NOT NULL
```

参照列の名前は、参照先ノートテーブルの単数名からプレフィックスを除いた部分に `_id` を付けたものにします。たとえば `zettelkasten_fleeting` を参照するなら `fleeting_id REFERENCES zettelkasten_fleeting(id)`、同様に `todo_task` なら `task_id`、`diary_entry` なら `entry_id` です。

`label` はそのプロパティ行の人間可読な表示値です。汎用クライアントが行に対して必ず表示できる唯一の文字列（タグ名、ファイル名、リンクタイトルなど）を指します。表示値を持たない一対多の関係はプロパティテーブルではなく、規約2の通常の追加テーブルとして表現してください。

note.db はプロパティテーブルに一意性を含意しません。意味に応じて主キーや UNIQUE 制約を張ってください。たとえばノートが各タグを高々1つだけ持つタグなら `(task_id, label)` を一意にし、同じファイル名が正当に重複しうる添付では一意にしない、といった具合です。

それ以外のカラムはフォーマット設計者の自由です（規約5により nullable またはデフォルト値付き）。プロパティテーブルは、別の note table への FK を任意のカラム名で追加で持ってかまいません。

ノートテーブルを参照するがこの形に当てはまらないテーブルはプロパティテーブルではなく、note.db は制限を設けません。

### 5. 拡張性

- ノートテーブルおよびプロパティテーブルにおいて、note.db が定めるカラム以外のカラムは nullable にするか `DEFAULT` を持たせてください。同じデータベースファイルは、更新時期の異なるクライアントや、note.db が定めるカラムだけを知るツールに共有されます。必須の追加カラムは、そのカラムを知らないすべての書き込み手を壊します。対話的なエディタと違い、旧バージョンのクライアントは不足値の入力を促して回復することができません
- note.db が定めるカラムの制約を強めること（例: 方法論上見出しが本質であるフォーマットでの `title` への `NOT NULL` 付与）は禁止しません。ただしトレードオフがあります: そのテーブルには、note.db の最小形しか知らないツールが盲目的に書き込めなくなります。対話的なエディタは制約エラーから不足値の入力を促して回復できますが、非対話の書き込み手（キャプチャツールやインポータ）は回復できません
- 既存カラムの型変更・削除は、同じデータベースを読み込むツールや他バージョンのフォーマットとの互換性を壊すため非推奨です
- note.db が定めないことはフォーマット設計者が自由に決めてかまいません

## note.db が意図的に定めないこと

note.db を最小限かつメソドロジー非依存に保つため、以下は規約の対象外とします。

- DB レベルの整合性強制の義務化
- CRUD 操作の実装方法
- フォーマットのバージョン間のマイグレーション
- ビューの提供義務
- 特定メソドロジーの表現方法
- UI や表示に関するヒント

## フォーマットを公開するには

1. note.db を満たす DDL ファイル（`format.sql`）を用意します。
2. 設計意図を記述した `spec.md` を用意します。
3. 任意のリポジトリで公開します。

フォーマット名はそのままテーブルのプレフィックスになります（規約3）。同じデータベース上の他フォーマットと衝突しにくい固有な名前を選んでください。note.db はバージョン命名の規約を定めません。破壊的変更を旧リリースのデータと共存させたい場合は、別名で公開してください。
