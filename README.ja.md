## note.sql とは

note.sql は、SQLite をパーソナルナレッジの基盤として使うための共通規約です。

タスク、メモ、アイデア、日記。これらを束ねるデジタル手帳には、ポータブルで永続的なオープン共通規格が存在しません。既存のノートツールはアプリごとに固有のフォーマットでデータを保存しており、ここに空白があります。

note.sql は、この空白を埋めるための共通規約を定めます。ノートを表すテーブルの最小構造や命名のルールといった土台のみを規定し、具体的な表現は各フォーマット（特定のメソドロジーを表す DDL 群）に委ねます。共通の土台があることで、複数のフォーマットが同じ SQLite ファイルに共存し、ツールはフォーマットを越えて動作します。

ライブラリでも CLI でもアプリケーションでもなく、規約そのものです。誰でもこの規約に従ってフォーマットを公開したり、ツールを作ったりできます。

## なぜ SQLite か

思考の痕跡には、アプリより長い寿命が必要です。どのアプリが廃盤になっても、どのサービスが終了しても、手元に残り続けるべきものだからです。

SQL は数十年の実績を持つ、枯れたオープン規格です。書き留めた断片をビューで束ね直し、集計で傾向に気づき、検索で過去に立ち返る。手帳をめくり、思い出し、繋げ直すための語彙が、標準仕様の範囲で揃っています。

SQLite はその SQL を、単一ファイルで完結し、あらゆる環境で読み書きできる形で実装した、事実上の標準です。

同じ動機は、Markdown のようなファイル群でも一見満たせます。けれどファイルは独立した文書であり、横断して束ねる共通の手段を持ちません。タグや関係をどう表現するかはフロントマターやフォルダ構造といったゆるい慣習として個々のファイルとユーザーの規律に委ねられ、その慣習自体を配布し、別のツールで一貫して効かせる手立てもありません。note.sql ではその役割を SQLite のスキーマに担わせます。フォーマットは DDL という配布可能な成果物であり、データベースを開いた時点で構造として効き、集計や横断検索は SQL として最初から備わっています。

## 規約

### 1. ノートテーブル

note.sql の中心概念はノートテーブルです。以下のカラムを少なくともすべて持つテーブルをノートテーブルと呼びます。

```sql
id         TEXT PRIMARY KEY  -- UUID 推奨
title      TEXT              -- nullable
body       TEXT NOT NULL
created_at TEXT NOT NULL     -- ISO 8601
updated_at TEXT NOT NULL     -- ISO 8601
```

フォーマットはノートテーブルを1つ以上持たなければなりません。

`body` はノートの内容そのものであり、必須です。`title` は任意の見出しです。走り書き、日記、fleeting note など、多くのノートは本文だけで成立し、見出しを付けること自体がすべてのメソドロジーにあるとは限らない編集行為だからです。

ノートテーブルをどう使うかはフォーマット設計者が自由に決めてかまいません。たとえば Zettelkasten であれば、ノートテーブルを1つ持ちリンクを別テーブルで管理することも、種別（literature note / permanent note 等）ごとにノートテーブルを分けることも、どちらも規約を満たします。

### 2. 追加テーブル

フォーマットはノートテーブル以外のテーブル（タグ、リンク、設定など）を持ってもかまいません。複数のフォーマットが同一の SQLite データベースに共存できるため、テーブル名・ビュー名はすべて規約3のプレフィックスルールに従い、名前の衝突を防いでください。

### 3. プレフィックス

テーブル名とビュー名にはフォーマット名のプレフィックスを付けます。SQL 識別子はハイフンを使えないため、フォーマット名にハイフンが含まれる場合はプレフィックスではアンダースコアに置き換えます（例: フォーマット `cornell-notes` のプレフィックスは `cornell_notes`）。

プレフィックスより後ろの部分は単数形にします（例: `..._note`, `..._task`, `..._tag`。`..._notes` のような複数形は使いません）。名前が揃ううえ、プロパティテーブルの参照列名を `<テーブル名>_id` と機械的に導出できます（規約4参照）。

```
<format>_<table>      -- 例: zettelkasten_note, evergreen_note
<format>_<view>_view  -- 例: zettelkasten_graph_view（ビューは推奨、必須ではない）
```

### 4. プロパティテーブル

プロパティテーブルは、ノートに紐付くラベル付きの一対多の関係を表現します。以下をすべて満たすテーブルをプロパティテーブルと呼びます（フォーマットが `zettelkasten`、プレフィックスを除いたテーブル名が `fleeting` であるノートテーブル `zettelkasten_fleeting` に紐付くプロパティテーブルの例）。

```sql
fleeting_id  TEXT NOT NULL REFERENCES zettelkasten_fleeting(id)
label        TEXT NOT NULL
```

参照列の名前は、参照先ノートテーブルの単数名からプレフィックスを除いた部分に `_id` を付けたものにします。たとえば `zettelkasten_fleeting` を参照するなら `fleeting_id REFERENCES zettelkasten_fleeting(id)`、同様に `todo_task` なら `task_id`、`diary_entry` なら `entry_id` です。

`label` はそのプロパティ行の人間可読な表示値です。汎用クライアントが行に対して必ず表示できる唯一の文字列（タグ名、ファイル名、リンクタイトルなど）を指します。表示値を持たない一対多の関係はプロパティテーブルではなく、規約2の通常の追加テーブルとして表現してください。

note.sql はプロパティテーブルに一意性を含意しません。意味に応じて主キーや UNIQUE 制約を張ってください。たとえばノートが各タグを高々１つだけ持つタグなら `(task_id, label)` を一意にし、同じファイル名が正当に重複しうる添付では一意にしない、といった具合です。

それ以外のカラムはフォーマット設計者の自由です（規約5により nullable またはデフォルト値付き）。プロパティテーブルは、別の note table への FK を任意のカラム名で追加で持ってかまいません。

ノートテーブルを参照するがこの形に当てはまらないテーブルはプロパティテーブルではなく、note.sql は制限を設けません。

### 5. 拡張性

- ノートテーブルおよびプロパティテーブルにおいて、note.sql が定めるカラム以外のカラムは nullable にするか `DEFAULT` を持たせてください。これにより、note.sql が定めるカラムだけを知るクライアントでも有効な行を挿入できます
- 既存カラムの型変更・削除は、同じデータベースを読み込むツールや他バージョンのフォーマットとの互換性を壊すため非推奨です
- note.sql が定めないことはフォーマット設計者が自由に決めてかまいません

### 6. format.sql の再適用可能性

`format.sql` はフォーマットの完全な最新定義です。加えて、すでにデータが入っているデータベースへ再適用しても安全であること――失敗も破壊もせず、データベースを最新定義へ収束させること――を推奨します。

- テーブルとインデックスは `CREATE ... IF NOT EXISTS` を使い、既存のものに対しては再適用が no-op になるようにします
- ビューは `DROP VIEW IF EXISTS` してから `CREATE VIEW` し、常に最新定義になるようにします

ビューは状態を持たないため、`format.sql` の再適用がそのままビュー定義の更新手段になります。これによりビューの陳腐化はフォーマットの関心事から消え、マイグレーションがやるべきことは既存テーブルの変形だけになります。その変形をどう実行するかは note.sql の対象外です。

### 7. バージョン宣言

フォーマットは `<format>_meta` テーブルを持つことを推奨します。少なくとも `schema_version INTEGER NOT NULL` を持つ単一行のテーブルで、フォーマットの現在の版数を宣言します。

```sql
id             INTEGER PRIMARY KEY CHECK (id = 1)  -- 単一行
schema_version INTEGER NOT NULL
```

追加のメタデータはカラムとして持たせます（規約5に従い nullable または `DEFAULT` 付き）。単一行の強制は、上記の `CHECK (id = 1)` のような制約で表現できます。

note.sql は複数フォーマットが同一データベースに共存することを前提とするため、`PRAGMA user_version` のようなデータベース全体で1つの印は原理的に使えません。バージョンはフォーマットごとに持つしかなく、それはプレフィックス付きのテーブルを意味します（規約2・3）。汎用クライアントはこのテーブルを1回引くだけで、任意のフォーマットのバージョンを検出できます。

規約5の範囲に収まる互換進化では `schema_version` を進めてください。破壊的変更は別名で公開します。

## note.sql が意図的に定めないこと

note.sql を最小限かつメソドロジー非依存に保つため、以下は規約の対象外とします。

- DB レベルの整合性強制の義務化
- CRUD 操作の実装方法
- フォーマットのバージョン間のマイグレーション（定めるのはバージョンの宣言方法のみ。規約7）
- ビューの提供義務
- 特定メソドロジーの表現方法
- UI や表示に関するヒント

## フォーマットを公開するには

1. note.sql を満たす DDL ファイル（`format.sql`）を用意します。
2. 設計意図を記述した `spec.md` を用意します。
3. 任意のリポジトリで公開します。

フォーマット名はそのままテーブルのプレフィックスになります（規約3）。同じデータベース上の他フォーマットと衝突しにくい固有な名前を選んでください。破壊的変更を別名で公開するとき（規約7）も同様です。それ以上のバージョン命名の規約を note.sql は定めません。
